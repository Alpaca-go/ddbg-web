## 0. 一页摘要

- **结论**：可以做，但这是一个**中高难度（4/5）**、内容量很大的项目。最大的瓶颈不在写代码，而在**卡牌数据**：TTS 模组 JSON 里**没有任何卡牌数值或文字**，所有数据都只存在于卡图上，必须用「视觉辅助转录 + 人工抽检」录入。**（2026-10-06 修订：Kyries 提供的印刷 PDF 中卡面文字和数字是真实可提取文本，转录工作大部分可改为自动提取，剩下的主要是图标语义映射和板块标注，见「附录：印刷 PDF 资料评估」。）**其次是**规则 PDF 文字提取会丢失图标**，大量数值紧跟在图标后面（伤害、压力、金币、伤口等），规格书要对照页面图像逐条核对。
- **策略**：先做核心盒（遗迹 Ruins + 最暗地牢 Darkest Dungeon），走通完整战役后，再按地点扩展（Weald、Warrens、Cove、Crimson Court）、独立模式（The Color of Madness）、小型扩展（Master Webber）、PvP（Butcher's Circus）的顺序推进。
- **架构**：纯 TypeScript 规则引擎（不依赖 React，确定性、可设种子、可回放，带测试）+ 数据管线（TTS JSON → 资产清单 → 切图 → 转录 → 校验 → 规范化游戏数据 JSON）+ React/Tailwind UI。
- **工作流**：助手负责分析、规格书、任务拆分和审查；Cursor 云端代码代理按任务开 PR 实现；Kyries 在三个检查点审批：规则规格确认、数据抽检、每个阶段的可玩验收。
- **时间（2026-10-06 第二次修订）**：Kyries 每周可投入 **30 小时以上**，并且卡牌数据改为从印刷 PDF 提取。按 **2026-10-12（周一）开工**估算：可玩单场战斗约 **5–7 周（2026-11-13 ~ 11-27）**；核心盒完整战役 v1.0 约 **12–18 周（2027-01-01 ~ 02-12）**；含全部扩展约 **19–30 周（2027-02-19 ~ 05-07）**。Kyries 的时间已经不是瓶颈，工期主要受四件事限制：代码代理的实现吞吐（PR、CI、修 bug 往返）、阶段之间的串行依赖、规则歧义裁定、板块手工标注。所以投入时间翻了三倍，工期只缩短约 25–30%。详见 §6。

### 1.2 规则书要点（已读，用作规格书基础）

**游戏结构**
- 战役共 4 幕。第 1–3 幕：每幕 2 个普通任务 + 1 个 Boss 任务（「Face the Threat」）；击败 Boss 后战役等级 +1。第 4 幕：最暗地牢任务（16 个房间，地牢规模翻倍，有 3 个「Excavation Site」房间）+ 最终战（Heart of Darkness；共 4 个形态，打其中 3 个，跳过哪个由此前完成的任务决定）。规则书称之为「11 个任务、4 幕」的战役。
- 失败条件：驿站（Stagecoach）没有可补充的英雄，凑不满 4 人；或者 Boss 任务失败。
- 每个 Boss 分 3 个等级，每级 3 张卡：描述卡、能力卡（威胁面分「地牢 / 村庄」两侧，另一面是战斗能力）、战斗卡。Boss 的被动威胁在击败前持续影响地牢和村庄。
- 难度模式：Radiant（简单：开局 20 金而不是 10；进地牢前的补给每人掷 1 颗，另 1 颗自选面；探索每人掷 1 颗骰，侦察后为 0 颗）和 Stygian（困难：开局 0 金币、改用 Stygian 房间卡、所有 Boss 技能 +1 Crit）。

**地牢循环**：侦察（全员 +1 压力，揭示相邻房间，下次探索每人只掷 1 颗探索骰）→ 探索走廊（每名英雄掷 2 颗探索骰，按姿态顺序结算：Curio / Trap / Rubble / Hunger / Stressful Darkness，可以用补给抵消）→ 进入房间（Empty / Trap / Dark / Lair / Curio（d10：1–5 有守卫）/ Treasure（胜利后 +20 金）/ Objective）。原路返回时每条走廊全员 +1 压力；长走廊有中途停靠点；可以在掷探索骰之前选择撤离；在已清理的房间用柴火（Firewood）休息。补给池上限 16 颗骰，种类有 Food / Bandages / Potion / Torch / Tool / Wild。

**战斗循环**
- 翻开房间卡和房间板块（Room Tile，上面分若干 Area，有容量、高低地、宝箱/交互点）。
- 英雄与怪物都有**双重位置**：姿态轨（Aggressive / Defensive / Ranged / Support）+ 板块上的区域。Push/Pull 同时改变两者。
- 生成怪物：从怪物牌堆抽牌，前排怪从前往后、后排怪从后往前填姿态位；大型怪占 2 格。
- 先攻：先攻牌堆 = 4 张英雄牌 + 每只怪物 1 张；抽到「英雄」就由姿态顺序上下一个还没行动的英雄行动。第 4 轮结束还没清场就被迫撤退。Boss 战不计轮数，Boss 每轮可行动多次。
- 英雄回合：开始阶段结算苦难/美德掷骰，每个状态堆叠移除顶层 1 枚并结算；然后有 2 个行动：移动（Speed）、交互、换姿态、使用技能（命中后同一回合不能再用同一技能）。补给可以作为免费行动使用。
- 命中判定：d10 ≤ Acc − 目标 Dodge 即命中；≤ Crit 值即暴击（暴击不受 Dodge 影响）。英雄打出暴击，同区英雄回复 1 压力；英雄被暴击，同区未被选为目标的英雄 +1 压力。多目标只掷一次。
- 状态（堆叠代币，每堆按持续回合数放代币）：Bleed、Blight、Stun、Buff（每堆 +1 Crit）、Debuff（攻击者每堆 +1 Crit）、Riposte（反弹一半伤害，向上取整）、Guard（必须优先攻击它）、Mark（攻击者每堆 +1 Acc）、Protection（伤害减半，向上取整）。抗性使持续时间 −1（对位移则 −1 格），免疫则完全无效。
- 怪物 AI：技能由所在姿态决定（有多个可选时掷 d10）→ 按目标优先级选目标（Closest / Furthest / Crowded / Most Wounded / Most Stressed / Marked→Closest 等，平手按姿态顺序，Guard 优先）→ 按 Speed 移动到射程内，到不了就跳过 → 结算。

**角色状态**
- 死门（At Death's Door）：伤口达到生命值后不再累积伤口，之后每次受伤改掷死门骰，出骷髅即死亡。多个持续伤害同时结算时只掷一次。（PvP 规则写着「骷髅当安全、空白当死亡，因此 PvP 死亡率为 7/10」，由此推断普通模式约为 3/10；骰面构成**待确认**。）
- 压力：上限 10。第一次到 10 时检定意志：d10 掷 1–2 获得美德，3+ 获得苦难，然后压力归零；已有苦难或美德时再到 10 就心脏病发死亡。返回村庄后，苦难转为 1 个负面怪癖，美德转为 1 个正面怪癖。
- 怪癖最多 3 个；第 4 个负面怪癖等于发疯，永久死亡。疾病同时只能有 1 个，再得新疾病时替换旧疾病，并额外获得 1 个负面怪癖。
- 饰品携带上限 = 英雄等级。饰品有正反两面，使用后翻面；战斗中每回合限用 1 次。
- 经验：任务给 0–3 XP，回村时发放，并同步累加到驿站，供新英雄继承。英雄和每个技能各有 3 个等级。

**村庄阶段**：抽村庄事件（决定准备天数）→ 每天开始时掷 d10 决定看守人（Caretaker）占用哪栋建筑 → 英雄按姿态顺序访问建筑（每栋建筑每天只能 1 人，每次访问做 1 个选项），也可以改用英雄的「村庄技能」。建筑有 Abbey、Tavern、Sanitarium、Survivalist、Guild（升级英雄/技能，不可升级）、Graveyard（不可升级）、Blacksmith、Nomad Wagon（饰品买卖）、Stagecoach（不可访问）。建筑升级费用为 20 金（Blacksmith 和 Nomad Wagon 为 10）。存档用纸质存档表，Web 端要对应设计存档结构。

**其他**：Abomination（人形/兽形切换）、PvP 模式「Butcher's Circus」（选秀、轮流激活，有 Puppets/Butcher 可选规则）、推荐队伍配置。

### 1.5 关键判断：卡牌数据能否从 JSON 提取？

**不能。** JSON 只提供：图片 URL、图集网格、牌组和背包的组织结构（可据此推断卡牌类别：怪物/Boss/房间/任务/饰品/怪癖/疾病/事件/英雄等），以及约 30% 卡牌的英文名。**所有数值（Acc、Crit、伤害、射程、姿态位、生命、闪避、速度、抗性、免疫、技能效果文字）都只在卡图上**，而且大量使用图标（见上方 Aimed Shot 样例：射程、目标、伤害、Crit、Acc 都是图标加数字）。

因此必须走**「切图 → 视觉辅助转录（带图标图例）→ 结构化 JSON → 校验器 → Kyries 抽检」**这条路。房间板块（区域、容量、高低地、交互点）和地牢板块（房间与走廊的连通图）也要从图片标注。

## 2. 难度评估

### 2.1 总评：**4 / 5（中高）**

规则本身是中等复杂度的战术桌游，但它同时包含：战役养成、程序化地牢、带位置和堆叠状态的战斗、怪物 AI、20 多个各有专属脚本的 Boss，以及上千张只有图片的卡牌。工作量主要在「内容」，引擎框架本身不算难。

### 2.2 分系统难度

| 子系统 | 难度 | 说明 |
|---|:---:|---|
| 卡牌数据录入（约 1,100 张牌面 + 板块） | ★★★★★ | JSON 里没有数据；靠视觉转录 + 图标图例 + 人工抽检；工作量最大，错误率决定可玩性 |
| 战斗引擎（先攻/姿态/区域/命中/状态/位移/大小型怪） | ★★★★ | 双重位置（姿态轨 + 区域）与位移、容量、大型怪挤占的交互最容易出错 |
| 怪物 AI（选技能/选目标/移动） | ★★★ | 规则清晰，但平手、Guard、Marked→Closest 等组合要逐条写测试 |
| Boss 专属规则（核心盒 4 个遗迹 Boss + 最暗地牢 3 个 + 最终战 4 形态；扩展 13 个；CoM 3 个；Master Webber） | ★★★★ | 每个都要定制脚本（召唤、传送、长椅、火刑柱、多形态等） |

### 2.3 最大风险

1. **卡牌数据提取（最高风险）**：JSON 里没有数据；图标语义要先建立图例（伤害、压力、治疗、目标、射程、姿态位、状态等）；转录会有错漏。缓解办法：按类别定 schema；双路转录（两次独立转录后比对差异）；在校验器里核对规则书写明的数量（如核心盒「231 张英雄技能卡 / 23 张英雄卡 / 168 张怪物与 Boss 卡 / 38 张饰品 / 17 正 + 18 负怪癖 / 11 疾病 / 5 苦难 + 5 美德 / 24 Curio / 16 村庄事件 / 19 任务 / 17 房间卡 / 17 Stygian 房间卡 / 8 Boss 房间卡 / 13 房间板块 + 1 PvP 竞技场 / 12 地牢板块 + 2 最暗地牢板块」）；做一个「卡图与 JSON 并排」的抽检页面。
   - **修订（印刷 PDF）**：卡名、数值、效果文字、风味文字都可以从印刷 PDF 直接取文本（嵌入字体 Ubuntu / DwarvenAxeBB，每页一张卡），不需要视觉识别数字，「转录错漏」风险明显下降。剩下的风险换成两项：① **图标语义**（状态、伤害类型、站位/目标点、压力等全是嵌入位图，不是字体字形，要建一次图标字典）；② **板块几何**（地牢/房间板块的区域划分在美术图里，仍需人工标注）。风险等级从「最高」降为「高」。
2. **规则 PDF 图标丢失与排版碎片**：提取的文字里，大量「Spend 1 [图标]」「suffer 2 [图标]」的图标都没了；核心规则书中还夹着法语残留（如 Nomad Wagon 段落里的「Gagner une vertu…」）和拼写错误（如「Sispersion」）。缓解办法：规格书每条都标注页码，对照页面图像核对；有疑问一律列为**待确认**。
3. **规则歧义**：初步识别的热点有：大型怪挤占与容量；位移被截断时姿态轨是否仍然移动；英雄先攻牌「下一个未行动者」与中途阵亡、多余先攻牌的处理；Boss 多次行动与姿态变化；抗性对位移的折算；死门时多个持续伤害只掷一次；饰品「每回合一次」与翻面时机；光照各档效果（图标表）；Guild 升级费用里的图标（应为金币，**待确认**）；陷阱攻击「Acc 8 / Crit 2」如何随地牢等级缩放（原文图标缺失，**待确认**）。缓解办法：允许引用模组里的 FAQ 和设计师 FAQ；仍有分歧的由 Kyries 在 `rulings.md` 中裁定（标注为「本项目裁定」）。
4. **扩展交互**：多地点混搭的牌堆组成、新机制（零容量区域、Impassable Walls、禁疗真菌）与 Boss 脚本叠加。缓解办法：引擎设计时预留「地点模块」接口，核心盒完成后再逐个接入，每个扩展都有独立的回归测试。
5. **美术版权与公开部署**：所有美术来自 TTS 创意工坊（版权属于原游戏和桌游发行方），**不适合公开部署或开源附带美术**。建议仓库设为私有，或者美术不进仓库（由本地脚本从 Steam CDN 拉取并缓存）；如需公开，换成占位美术。具体策略**由 Kyries 决定**。另外，Steam CDN 链接可能失效，应尽早把资源缓存到本地私有存储。
6. **范围蔓延**：联机多人、动画特效、手机适配、AI 队友、多语言（中文化）都会显著拉长周期。建议首版只做**单设备、1–4 人轮流操作（hot-seat）、英文卡面 + 中文 UI**，其余放进后续清单。

## 3. 推荐技术栈与架构

### 3.1 技术栈（沿用 Kyries 熟悉的组合）

- **Vite + React + TypeScript + Tailwind CSS**
- 状态：引擎状态是不可变数据，UI 层用 **Zustand** 包一层（只负责订阅和派发命令）
- 校验：**Zod**（数据 schema 与存档 schema）
- 测试：**Vitest**（引擎单元测试与场景测试）+ **Playwright**（每个阶段 1–3 条关键路径冒烟测试即可，不做全量回归墙）
- 工具：pnpm workspaces（或 npm workspaces）、ESLint + Prettier、GitHub Actions（typecheck、lint、test、build）
- 可选：XState（只在最外层流程状态机需要可视化时考虑，默认用判别联合 + reducer）

### 3.2 仓库结构（monorepo，但保持轻量）

```
ddbg/
  packages/
    engine/        # 纯 TS 规则引擎：不依赖 React/DOM
    data/          # Zod schema + 生成的规范化 JSON（heroes, skills, monsters, bosses, rooms, tiles, quests, trinkets, quirks, diseases, curios, events…）
  apps/
    web/           # React + Tailwind UI
  tools/
    pipeline/      # TTS 解析、图片缓存与切图、转录辅助、校验器、抽检页面生成
  docs/
    rules-spec/    # 规则规格书（中英术语对照，标页码）
    rulings.md     # 本项目裁定（对应 FAQ 或 Kyries 决定）
    data-legend.md # 卡面图标图例
```

### 3.3 规则引擎设计

- **确定性**：所有随机数（d10、探索骰、补给骰、死门骰、洗牌）都走可设种子的 RNG；同样的种子加同样的命令序列 = 同样的结果。这让存档就是「初始种子 + 命令日志」，方便回放、复现 bug 和写测试。
- **命令 → 事件模型**：`applyCommand(state, command) → { state, events[], pendingChoice? }`。凡是需要玩家决策的地方（选目标、分配休息点、选择哪颗骰先结算、是否用饰品等）都返回 `PendingChoice`，UI 只负责呈现选项。
- **分层状态机**：`Campaign → Hamlet(Day loop) → QuestSelect → Dungeon(Explore / Corridor / Room) → Battle(Round → Turn → Action) → ReturnToHamlet`，每层是判别联合类型。
- **数据驱动的效果系统**：效果原语（伤害、治疗、压力 ±、加状态堆叠、移除状态、位移、召唤、换姿态、抽牌、光照 ±、获得金币/补给等）+ 触发钩子（onDamaged、onHealed、onStress、onLightChange、onTurnStart、onCrit、onShuffled、onConsumeProvision 等），覆盖怪癖、疾病、饰品、苦难/美德。**Boss 专属逻辑允许写 TS 脚本**（每个 Boss 一个模块），不强行塞进 DSL。
- **测试**：规则书里的例子直接做成黄金测试（如 Hellion 用 Iron Swan 打 Bone Arbalist：Acc 9 − Dodge 1 → 掷 ≤ 8 命中；Vestal 的 Divine Comfort II 暴击；Highwayman 的 Bleed 堆叠例子；Shuffling Horror 一轮两次行动的先攻例子）；每个子系统都有场景测试；数据加载时跑完整性校验。

### 3.4 数据管线（TTS JSON → 规范化游戏数据）

1. `tts-parse`：解析模组，输出**资产清单**（每个对象：类型、背包路径、名称、图集 URL、网格、CardID → 格子坐标、所属类别推断）。
2. `assets-fetch`：用 GET 拉取并本地缓存全部图片（不要用 HEAD），记录哈希；**整张图集切片**（不只切被引用的格子）。
3. `classify`：按背包路径和卡背把卡片归类（英雄卡/技能卡/怪物/Boss 三类卡/房间卡/任务/饰品/怪癖/疾病/Curio/村庄事件/苦难美德/先攻/玩家辅助卡），人工确认归类表。
4. `transcribe`：视觉辅助转录。按类别固定 schema 加上图标图例，每张卡输出 JSON 草稿和置信度；低置信字段标 `needsReview`。两次独立转录后自动比对差异。
5. `validate`：Zod 校验；交叉引用（技能所属英雄、怪物等级、Boss 召唤物是否存在等）；数量对账（对照规则书部件清单）；数值范围检查。
6. `review-page`：生成静态抽检页（左边卡图，右边 JSON），Kyries 按抽样比例勾选「通过 / 有误」。
7. 板块标注：房间板块（区域多边形、容量、高低地、交互点、出生点）和地牢板块（房间节点、走廊、长走廊停靠点、边缘房间、Boss 位）用一个简易标注工具（浏览器内点选）生成 JSON。

## 5. 开发顺序与阶段

> 工期按「日历周」估算（2026-10-06 第二次修订）。前提：Cursor 云端代码代理可以并行处理 2–3 个任务；Kyries 每周投入约 30 小时，负责审阅、裁定、试玩，也亲手做图标标注和板块标注。每个阶段写成「新工期（原工期）」；原工期是第一版的估算，当时假设 Kyries 每周只有 6–10 小时。相邻阶段可以部分重叠，见 §6。

### Phase 0：项目基建 + 规则规格书 v1（核心盒）
- **目标**：搭好新仓库骨架；产出一份可审阅的核心规则规格书。
- **任务**：建立 monorepo、CI、代码规范、PR 模板和 issue 模板；规格书覆盖战役/村庄/地牢/战斗/状态/压力/死亡/Boss 通用流程（标页码，中英术语对照）；初版待确认清单；初版图标图例（从卡图和规则书截取）；确定美术策略和仓库可见性。
- **交付物**：可运行的空壳应用（`npm run dev`）；`docs/rules-spec/core.md`；`docs/rulings.md`（空模板）；`docs/data-legend.md`。
- **验收标准**：CI 全绿；规格书覆盖 §1.2 列出的全部机制；每条待确认项都有编号。
- **Kyries 需要提供**：确认范围（hot-seat、英文卡面 + 中文 UI 是否 OK）、仓库可见性与美术策略、逐条确认规格书和待确认项（**检查点 ①**）；如能找到 FAQ，一并提供。
- **工期**：**1.5–2 周**（原 1.5–2.5 周），**与 Phase 1 并行**｜Kyries 投入约 10–12 小时/周用于逐条确认规格书。

### Phase 1：数据管线 + 核心盒数据
- **目标**：核心盒（遗迹 + 最暗地牢 + 通用卡 + 核心盒英雄）的全部数据结构化。
- **任务**：实现 tts-parse / assets-fetch / 切图 / 分类；定好各类别 schema；转录核心盒英雄卡与技能卡、怪物与 Boss 卡、房间卡（含 Stygian）、任务、饰品、怪癖、疾病、Curio、村庄事件、苦难/美德；标注核心盒房间板块和地牢板块；校验器加数量对账；生成抽检页。
- **交付物**：`packages/data` 中的核心盒 JSON；抽检页；转录差异报告；数量对账报告。
- **验收标准**：Zod 全部通过；数量与规则书部件清单一致（或差异有解释）；Kyries 抽检错误率达标（建议：随机抽 10%，关键数值错误 ≤ 2%，否则返工这一批）。
- **Kyries 需要提供**：**检查点 ②** 数据抽检；对看不清的卡面给出判断（必要时参考实体卡）。
- **工期**：**1.5–2.5 周**（原 2.5–4 周），**与 Phase 0 并行**｜Kyries 亲手做图标字典标注（约 1–2 天）和核心盒板块标注（28 面，约 2–3 天），外加抽检。任务里的「切图/视觉转录」换成「印刷 PDF 文本提取 + 版式解析 + 图标字典 + 板块标注」，见附录。

### Phase 2：战斗引擎 MVP + 最简战斗 UI
- **目标**：能完整打一场普通遭遇战（固定房间、固定英雄、遗迹怪物）。
- **任务**：区域与姿态双重位置模型；生成规则（前排/后排、大型怪）；先攻牌堆与轮次（4 轮撤退）；英雄 2 个行动（移动/交互/换姿态/技能）；命中与暴击（含暴击时的压力连带效果）；全部状态堆叠；位移；抗性与免疫；高低地；怪物 AI 三步；死门、心脏病、意志检定；战斗结束与战利品。UI 部分：板块与区域、姿态轨、卡牌信息、行动面板、战斗日志、种子/状态调试面板。
- **交付物**：可玩的「单场战斗」页面；引擎测试套件（含规则书例子做成的黄金测试）。
- **验收标准**：Kyries 能用 4 名核心英雄打完至少 3 种不同的怪物组合，没有卡死；规则书例子全部通过。
- **Kyries 需要提供**：**检查点 ③** 试玩验收；裁定战斗类待确认项。
- **工期**：**2.5–4 周**（原 3–5 周）。接口（GameState / Command / Event）定下来以后，UI 壳子可以和引擎并行开发；最多可以和 Phase 0/1 尾部重叠约 0.5–1 周（先用手写测试数据跑引擎）。战斗引擎是改动最集中的部分，PR 不宜大量并行。

### Phase 3：地牢探索
- **目标**：完成一次地牢任务：从入口探索到目标房间并撤离。
- **任务**：地牢板块图；房间代币随机分布；侦察、探索骰与危险结算、补给使用、原路返回、长走廊、撤离；各房间类型；房间卡与 Room Tile 联动；柴火休息；光照轨（效果表**待确认**后实现）；任务目标与 XP 结算。
- **交付物**：可玩的「单任务」流程（任务卡 → 地牢 → 战斗 → 结算）。
- **验收标准**：至少跑通 3 张不同的核心任务卡；撤离、失败、清场等分支都正确。
- **Kyries 需要提供**：试玩验收；确认光照表和陷阱缩放规则。
- **工期**：**1.5–2.5 周**（原 2–3.5 周），和 Phase 4 部分并行。

### Phase 4：村庄与战役循环 + 存档
- **目标**：任务 → 村庄 → 任务的循环；英雄死亡与驿站补充；存档与读档。
- **任务**：村庄事件与准备天数、看守人、各建筑服务与升级、Guild 升级、Graveyard、Nomad Wagon、Blacksmith 临时升级、村庄技能；苦难/美德转怪癖；驿站 XP 与新英雄继承；战役等级推进与牌堆切换（L1 → L2 → L3）；存档（种子 + 命令日志 + 快照，带版本号）。
- **交付物**：可以连续玩第 1 幕两个普通任务的战役。
- **验收标准**：存档后刷新能完整恢复；英雄死亡补充流程正确；Kyries 试玩第 1 幕前两个任务。
- **工期**：**1.5–2.5 周**（原 2–3.5 周）。村庄和存档只依赖战役状态模型，可以和 Phase 3 重叠约 1 周，两者合计约 3–4.5 周。

## 6. 时间预估（2026-10-06 第二次修订：每周 30 小时）

### 6.1 现在是什么在限制工期

第一版假设 Kyries 每周只有 6–10 小时，审阅和裁定排队是主要瓶颈。现在每周有 30 小时以上，这个瓶颈基本消失。剩下的限制按影响从大到小排：

1. **实现吞吐**：工作链是「助手拆任务 → 代码代理开 PR → CI → 助手审查 → 改 → 合并」，加上试玩发现 bug 后的返工。规则引擎的核心（状态模型、战斗结算）改动高度集中，PR 并行多了容易冲突，实际只能同时推 2–3 条互不相干的线。代理每周能合并多少个**合格的** PR，要到 Phase 0/1 实测后才知道；本估算按保守值算。
2. **阶段之间的串行依赖**：状态模型 → 战斗 → 探索 → 战役/村庄 → Boss，后一步依赖前一步的接口和测试。能重叠的只有：Phase 0 与 Phase 1；UI 壳子与引擎（接口定下来之后）；Phase 3 与 Phase 4；扩展的数据和标注与上一个扩展的试玩。
3. **规则歧义裁定**：Kyries 有时间以后裁定可以很快，但有些问题要翻规则书、查 FAQ，或者试玩后才能决定。建议阻塞类问题 24 小时内答复。
4. **人工审阅不能省**：助手审查所有 PR。但涉及规则正确性的引擎 PR、存档格式，以及 UI 交互，仍需 Kyries 看过（至少看测试用例和试玩结果）再合并。这部分审阅不会因为代理更快而消失。
5. **数据手工部分**：图标字典约 1–2 天；板块标注约 80 面，核心盒 28 面约 2–3 天，每个扩展约 1 天。这些由 Kyries 亲手做，可以和代理的开发并行，所以基本不在关键路径上，前提是提前做完。

### 6.4 每周 30 小时的节奏建议

**固定节奏**
- **周一**（约 1.5 小时）：和助手一起做周计划，确定本周 PR 队列、需要裁定的问题和试玩目标。
- **每天**（约 1–1.5 小时，固定在一两个时段）：清 PR 审阅队列，回答阻塞问题。
- **周五**（约 1.5 小时）：阶段验收或演示，看助手的周报（完成项、阻塞项、待裁定项、速度和剩余工期）。

**时间分配**

| 用途 | 起步期（第 1–3 周） | 开发期（第 4 周起） |
|---|---|---|
| 规格书确认 + 规则裁定 | 10–12 小时 | 4–5 小时 |
| 数据：图标字典、板块标注、抽检 | 10–12 小时 | 2–4 小时（各扩展开始前会上升到约 8 小时） |
| PR 审阅（规则正确性、测试用例、UI 交互） | 3–4 小时 | 8–10 小时 |
| 试玩（按验收清单跑，并记录 bug） | 0–2 小时 | 7–9 小时 |
| 计划、同步、看周报 | 3 小时 | 3 小时 |
| 机动（小修小补、补裁定、额外试玩） | 2 小时 | 2–3 小时 |

**原则**
- 让代理一直有活干：先完成会阻塞它们的事（裁定、标注），再做审阅，最后试玩。
- 试玩发现的问题当天记成 issue，并附种子和命令日志，方便复现。

### F.2 关键结论：卡面文字和数字可以提取

- 卡牌 PDF 都是 InDesign 导出的 PDF/X-4。**每页一张卡**（裁切框 = 卡面，四周 3 mm 出血），正反面按页码一一对应（例如技能卡背面第 1 页「CRUSADER / Smite / I」对应正面第 1 页「Smite I」）。所以**不需要切分卡片**，坐标都可以换算到裁切框内。
- 文字使用**嵌入的子集字体**（Ubuntu 系列 + DwarvenAxeBB），带 ToUnicode 映射，是**真文本**，不是转曲或位图：卡名、Crit/Acc 阈值、伤害数值、HP、目标描述（Most Wounded / Furthest）、位移（Push/Pull）、效果说明、Curio 和 Boss 的风味文字都可以直接取到，并带有精确坐标。
- **图标不是字体字形**，而是置入的位图，常见做法是一个图标叠 2–4 层（底框 + 图形 + 高光）。这包括站位/目标点、伤害类型、状态（流血、腐蚀、眩晕等）、压力、抗性和免疫、骰面等。它们有精确坐标，可以和相邻文字拼成一行，例如 `{icon:…} +1 vs Unholy`；但图标的含义需要建一次**图标字典**。实测：4 个卡牌文件里有 6,037 个合成图标，按感知哈希聚成约 628 类（其中出现 3 次以上的有 447 类）；全部文件约 4,780 个不同的图像摘要（同一个图标在不同文件里会重新编码）。按视觉聚类后人工标注，估计 **1–2 个工作日**。
- 少数文件**完全没有文字**（转曲或位图）：先攻卡（8 张）、任务地图卡（14 张）、英雄面板、怪物姿态板、骰子展开图。它们信息量很小，人工录入即可。
- 重复的必须去掉：InDesign 会把同一段文字输出两次（描边 + 填充），按「文字 + 坐标」去重。牌堆副本按整页文字比对去重：中型怪物 251 页里不同的有 137 页。
